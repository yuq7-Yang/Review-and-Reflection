# 工作复盘（周 / 月 / 年）

用日志重建事实，用框架逼出结论，落成一份自己会重读的文档。

## 三条规矩，先读

**1. 日志只是线索，不是事实全貌。**
日志通常只覆盖一小部分工作日。开会、打电话、即时通讯、当面协调、领导临时交办——全都不留痕。
所以任何"这个月主要在忙 X"的结论，必须同时有日志证据和用户确认。素材不足就写"无记录"，**不要用合理推测填补**。编出来的复盘比不写更有害。

**2. 不写表扬稿。**
禁止"收获很大""能力得到提升""顺利推进""效率显著提高"这类没有主语的句子。每条结论必须挂靠一个具体事件：哪件事、涉及谁、什么结果、下次怎么改。

**3. 返工和卡点是最高价值素材。**
日志里"第一版做错""用户要求重做""受限于…""返工"这类记录，全部提取到卡点章节。顺的部分一句话带过，不顺的部分展开写。复盘的用处全在后者。

## 流程

### 第 1 步：定周期

周期交给脚本算，**不要手算日期，也不要依赖 `date -d "last monday"` 这类文本解析**。实测在部分环境（Git Bash）下它会静默返回错误日期——`date -d "2026-11-07 last monday"` 返回周六 11-07，既不是本周一也不是上周一，而且不报错。

| 用户说 | 参数 | 扫到的区间 |
|---|---|---|
| 本周 / 这周 | `--period this-week` | 周一 ~ 今天 |
| 上周 | `--period last-week` | 上周一 ~ 上周日 |
| 本月 / 这个月 | `--period this-month` | 1 号 ~ 今天 |
| 上月 / 上个月 | `--period last-month` | 完整自然月 |
| 今年 | `--period this-year` | 1/1 ~ 今天 |
| 去年 | `--period last-year` | 完整自然年 |

任意区间用 `--since` / `--until` 显式指定。补做历史复盘时加 `--today YYYY-MM-DD` 把"今天"挪到那个时点。

默认规则（用户没说范围时）：
- 周五 / 周六 / 周日提问 → `this-week`
- 月初 1–5 号提问 → `last-month`
- 12 月下旬 / 1 月上旬提问 → `last-year`
- 其余情况直接问一句"复盘哪个区间"，问完就开工，不要反复确认

脚本返回的 `period` 字段（如 `2026-W45`）直接用来命名复盘文件，跨年周已按 ISO 规则处理，不会重名。

### 第 2 步：扫素材

先判断素材在哪，再选命令。**不要假设一定有本机日志**：

| 情况 | 命令 |
|---|---|
| 机器上有 `~/WorkBuddy/*/.workbuddy/memory/` 项目日志 | `python <本 skill 目录>/scripts/scan_activity.py --period last-week --pretty` |
| 日志在别处 | 加 `--root <目录>`（其每个一级子目录算一个项目） |
| 只有一个仓库 / 一个目录 | 加 `--root . --single`（把该目录本身当作一个项目） |
| 用 Obsidian / Logseq / 手写日记 | 加 `--notes <目录>`，可重复指定多个 |
| 三者都没有 | 跳过脚本，直接问用户这段时间做了什么 |

```bash
# 常见组合
python <本 skill 目录>/scripts/scan_activity.py --period last-week --pretty
python <本 skill 目录>/scripts/scan_activity.py --period this-month --notes ~/notes
python <本 skill 目录>/scripts/scan_activity.py --since 2026-10-01 --until 2026-10-31 --root . --single
```

`--notes` 认文件名以 `YYYY-MM-DD` 开头的 `.md`（`2026-11-07.md`、`2026-11-07-周记.md` 都行），会递归子目录。

**先看 `warnings`。** 出现「根目录不存在」「笔记目录不存在」说明没扫到东西，改路径；出现「条目超过 120 条」说明项目太大，缩小 `--root` 或换更短窗口。

JSON 到 stdout，摘要到 stderr（摘要里已含覆盖率）。重点读四处：

| 字段 | 用途 |
|---|---|
| `window.log_dates` | 哪几天有记录，据此判断覆盖率 |
| `totals` | 日志篇数 / 实质文件 / 成型交付物 |
| `projects[].logs[].outline` | 每篇日志的小节标题，先扫标题再决定读哪几篇 |
| `projects[].items` | 文件痕迹；`kind: "bundle"` 是素材堆（爬虫图片、批量抓文），直接跳过 |

**不要通读所有日志。** 先看 outline，挑出与周期相关的再读全文。日志里通常已经写好了任务、交付物、方法要点、返工记录，这是最好的原料。

脚本已经做过降噪：同一日期模式重复出现的文件标为 `routine`（自动化产物），成堆素材折叠成 `bundle`，`.md`/`.html` 不计入交付物。这些口径不要自己再算一遍。

### 第 3 步：补盲区

先算覆盖率 `log_days ÷ window.days`：

| 覆盖率 | 动作 |
|---|---|
| < 30% | 必须问："这段时间精力主要在哪几件事上？" |
| 30%–70% | 问："日志之外还有哪些事在跑？" |
| > 70% | 可以直接写，写完再给用户补漏 |

另外两种必问情况：
- 有成型交付物、但那天没有日志 → "这东西交付的过程里，有什么没记下来的？"
- 同一件事在日志里跨了好几篇但没结论 → "这件最后到底定了吗？"

一次最多问 3 个，只问影响结论的。

**问完再动笔。** 盲区问题属于过程，不属于交付物——成品里不该出现"待补充""待你回答"这类清单。用户答"没什么"或一直不答，就在文档开头标注覆盖情况，按现有素材写下去。

### 第 4 步：归类

把素材重组成三类，**不要按天罗列**：

| 类型 | 判定标准 | 写法 |
|---|---|---|
| 交付型 | 有成型产出：文档、方案、表格、上线的东西 | 逐项写清产出物和去向 |
| 推进型 | 没产出但推动了事：对齐口径、催进度、协调资源、拍板 | 主动追问，最容易漏记 |
| 消耗型 | 例行自动化、返工、重复劳动、无效会议 | 算占比，不逐条列 |

三类占比本身就是结论。如果一个月里消耗型占了大半，这个发现比写完十项成果更有价值——直接写出来。

### 第 5 步：写复盘

按周期读对应框架，**只读一个**：

- 周复盘 → [references/weekly.md](references/weekly.md)
- 月复盘 → [references/monthly.md](references/monthly.md)
- 年复盘 → [references/yearly.md](references/yearly.md)

如果工作区存在复盘档案（第 7 步维护的那个文件），先逐条核对里面「待兑现清单」的上期事项兑现情况，写进复盘。**这是复盘的复利所在，不能跳过**——没有对照的复盘，每期都在重新开始。

### 第 6 步：落成文档

先在本地写 `复盘-<周期标识>.md`（例如 `复盘-2026-W45.md`、`复盘-2026-10.md`、`复盘-2026.md`），用标准 Markdown：`#` / `##` / `###` 标题、Markdown 表格、有序列表。

**本地 Markdown 本身就是成品**——不要因为没接文档平台就不交付。需要放到在线文档时，按用户环境选一条：

| 目标 | 做法 |
|---|---|
| 飞书 | `lark-cli drive +import --file "<绝对路径>/复盘-2026-W45.md" --type docx --name "周复盘 2026-W45（11.02-11.08）"` |
| Notion / 语雀 / Obsidian | 把 Markdown 正文直接写入，或调用对应的 MCP 工具 |
| Word / PDF | 用 docx 技能或 pandoc 转换 |

走飞书时注意：
- 未认证先 `lark-cli auth login`
- 成功返回 `url`，把链接和一句摘要给用户
- 失败按错误类型处理：`missing scope` / 无权限 / 文件不存在 → 停止并报告，不要换身份反复试；`rate limit` / 网络抖动 → 最多退避重试 2 次

### 第 7 步：归档与结转

两件事必须做：

1. 复盘 md 留在当前工作区，文件名带周期标识，下次拿来对照
2. 更新复盘档案里的「待兑现清单」：删掉已兑现的，加入本期新定的 1–3 条

复盘档案默认放在工作区的记忆目录（WorkBuddy 为 `.workbuddy/memory/MEMORY.md`），换环境时放任意固定位置即可，只要下期能找到。文件里同时维护一份历史复盘索引：

```markdown
## 待兑现清单
| 立项周期 | 事项 | 验收标准 | 状态 |
|---|---|---|---|
| 2026-W45 | 方案的核心章节改成三档 | 出 v2 并在周会上过一遍 | 进行中 |

## 复盘记录索引
| 周期 | 文档 | 本地文件 | 备注 |
|---|---|---|---|
| 2026-W45 | <链接> | 复盘-2026-W45.md | 覆盖率 43% |
```

## 通用输出要求

- 开头三行：一句话定性这段时间 + 最大收获 + 最大问题
- 正文用事件说话，数字优先于形容词（"改了 5 版"胜过"反复打磨"）
- 结尾必须有"下期只做 3 件事"，超过 3 件等于没选
- 涉及对领导、同事的评价时，只描述行为和影响，不做人品判断

## 反模式

- 把文件列表当成果 → 那是审计，不是复盘
- 按日期流水账 → 读者只看到忙，看不到判断
- 只写顺利的部分 → 下期还会踩同一个坑
- 结论没有主语和动作 → "要加强沟通"是废话，"周三前把交付口径跟对接人书面确认"才是计划
- 素材不够就编 → 宁可交一份短的、标着"覆盖不足"的复盘
